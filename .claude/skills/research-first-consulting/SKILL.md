# Research-First Consulting

ユーザとの相談において「まず聞き、次に調べ、そして答える」を徹底するスキル。
ユーザの質問に対して、Claudeが自身の学習データだけで回答を完結させることを防ぎ、
常に最新の信頼できる情報に基づいた意思決定支援を行う。

---

## Phase 1: ヒアリング（Clarify Gate）

grill-me（usirin）のツリーウォーキング戦略と、prompt-improver（severity1）の曖昧/明確の自動判定ゲートを組み合わせたフェーズ。

### 判定: ヒアリングが必要か？

ユーザの質問を受け取ったら、以下の4項目をチェックする。
**1つでも不明な項目があればヒアリングを実施する。すべて明確ならスキップしてPhase 2へ。**

```
チェックリスト:
□ 意図の一意性   — この質問には1つの解釈しかないか？
□ 前提条件      — 技術スタック、予算、期間、対象ユーザ、地域など必要な前提が揃っているか？
□ 判断基準      — 何を重視して判断すべきか（コスト、速度、品質、学習コスト等）が示されているか？
□ スコープ      — 一度の回答で答えられる範囲に絞れているか？
```

### ヒアリング免除のケース

以下のいずれかに該当する場合はヒアリングをスキップし、直接Phase 2へ進む：

- 質問が十分に具体的で前提条件も明確に記述されている
- 過去の会話（メモリ）から必要な文脈がすべて推測できる
- 「ざっくり教えて」「概要だけ」のように精度より速度を優先している
- 「調べて」と明確にリサーチだけを指示している
- 会話の流れで前提が既に共有されている

### ヒアリングの実施ルール

**1回のメッセージで最大3問。** 何度も聞き返すとユーザの作業が進まない。

#### 質問の型

grill-meのQuestion Typesを相談文脈に適応させたもの。状況に応じて使い分ける：

**スコープ確認型**:
> 「〜を検討したい、とのことですが、対象はAの範囲ですか、それともBまで含みますか？」

**前提確認型**:
> 「いくつか確認させてください。技術スタックは〇〇で合っていますか？予算感やリリース時期の制約はありますか？」

**判断基準確認型**:
> 「選定にあたって特に重視するポイントはどれですか？」
> （選択肢を提示する：コスト / 開発速度 / 拡張性 / 日本語対応 / エコシステムの充実度 など）

**二者択一型**:
> 「AとBどちらに近いイメージですか？ それとも全く別のアプローチも検討対象ですか？」

#### 質問作成の原則

- **選択肢を提示する** — ユーザの認知コストを下げる。自由回答より選択式が望ましい
- **なぜ聞いているかを簡潔に説明する** — 「最適な提案のために確認させてください」の一言を冒頭に添える
- **メモリから推測できる前提は聞かない** — ユーザの技術スタック（React/Next.js, TypeScript, Python/FastAPI, AWS, Cloudflare等）、現在のプロジェクト文脈、過去の意思決定は既知情報として活用する
- **1つの質問に1つの論点** — 複合質問を避ける

#### ヒアリング後のまとめ

ユーザの回答を受け取ったら、理解した前提条件を以下の形式で簡潔にまとめ、認識が正しいか確認してからPhase 2に進む：

```
理解した前提:
- 目的: [何を達成したいか]
- 制約: [技術的制約、予算、期間等]
- 重視点: [判断基準の優先順位]
- スコープ: [対象範囲]

この理解で合っていますか？問題なければ調査に入ります。
```

**ただし、前提が明白でユーザの回答が十分に明確な場合は、確認ステップを省略してそのままリサーチに入ってよい。** 毎回確認を挟むと冗長になるため、本当に認識齟齬が起きそうな場合にのみ使う。

## Phase 2: リサーチ（Research Gate）

content-research-writer（ComposioHQ）のリサーチフローと、deeper-analysis（brunoasm）の多角的思考を組み合わせたフェーズ。

### 絶対ルール: 自分の学習データだけで回答を完結させてはならない

Claudeの学習データには以下のリスクがある：
- **鮮度リスク**: カットオフ以降に料金、API仕様、法制度、サービス存続状況が変わっている
- **確証バイアス**: 自身が「知っている」と確信している情報ほど検証を怠りやすい
- **単一視点リスク**: 学習データの偏りにより、特定のツール・手法を過大評価しがち

### リサーチ実施手順

#### Step 1: 検索計画を立てる

回答に必要な情報を分解し、検索クエリを計画する。

```
検索計画:
1. [広いキーワード] — 全体像の把握
2. [選択肢Aの具体的検索] — 公式ドキュメント・最新リリースノート
3. [選択肢Bの具体的検索] — 同上
4. [比較・ベンチマーク] — 第三者による比較記事
5. [日本語圏の事例] — 日本での採用事例・日本語ドキュメント状況
```

比較・選定の相談では、**各選択肢を個別に検索**して公平に情報を集める。
片方だけ深く調べて他方を浅く済ませてはならない。

#### Step 2: 検索を実行する

- **最低2回、通常3〜5回**のウェブ検索を実行する
- 必要に応じて`web_fetch`で公式ドキュメントの詳細ページを読み込む
- 検索クエリは**短く具体的に（1〜6語）**。まず広く、次に絞る

#### Step 3: 情報の評価と整理

取得した情報を以下の基準で評価する：

**情報源の信頼性ランク**（上位を優先）:

```
Tier 1（最優先）:
  - 公式ドキュメント・公式ブログ・リリースノート
  - 学術論文・政府統計・企業IR
  - 公式GitHubリポジトリ

Tier 2（信頼性高）:
  - 信頼性の高い技術メディア（公式著者による記事）
  - Stack Overflowの高評価回答
  - 著名な技術者のブログ（実名・所属明記）

Tier 3（補助的に使用、単独で根拠にしない）:
  - 個人ブログ・Qiita・Zenn等の個人記事
  - フォーラム・Reddit等のコミュニティ投稿
  - 匿名の情報源
```

**クロスチェック**:
- 重要な事実（料金、仕様、制度）は**最低2つの独立したソースで裏付け**を取る
- ソース間で矛盾がある場合は**両方を提示**し、ユーザに判断材料を渡す

**鮮度チェック**:
- 引用する情報の日付を確認し、回答中に明示する（「2025年10月のドキュメントによると」等）
- 日付が不明な情報はその旨を注記する
- 1年以上前の情報しか見つからない場合は、情報が古い可能性をユーザに伝える

#### リサーチ結果の整理テンプレート

内部的に以下の形式で整理してから回答を組み立てる（このテンプレート自体をユーザに見せる必要はない）：

```
## リサーチ結果

### 選択肢A: [名称]
- 公式情報: [URL] ([日付])
  - [主要な事実・数値]
- 第三者情報: [URL] ([日付])
  - [補足情報]
- 日本語対応状況: [情報]
- 料金: [具体的な数値]

### 選択肢B: [名称]
- 公式情報: [URL] ([日付])
  - [主要な事実・数値]
- 第三者情報: [URL] ([日付])
  - [補足情報]
- 日本語対応状況: [情報]
- 料金: [具体的な数値]

### ソース間の矛盾
- [矛盾点と各ソースの主張]

### 情報が見つからなかった点
- [調査したが確認できなかった事項]
```

### リサーチ免除のケース

以下の場合のみ、検索なしで回答してよい：

- 数学・論理の定理や証明（不変の知識）
- プログラミング言語の基本文法・構文（forループの書き方等）
- 日本語の敬語・英文法などの言語規則
- コードのロジックバグが明確なデバッグ（外部情報不要）
- ユーザが「検索しなくていい」「あなたの意見だけでいい」と明示した場合

**上記以外は、たとえClaudeが「知っている」と確信していても検索を実施する。**

特に以下は**必ず検索する**（古い情報で回答するリスクが高い）：
- 料金・価格体系（SaaS、クラウド、API課金等）
- API仕様・ライブラリのバージョン・破壊的変更
- サービスの現在のステータス・存続状況
- 法制度・税制・行政手続き（開業届、インボイス、確定申告等）
- 人事（CEO、大臣等の現職者）
- Cloudflare/AWS/Vercel等の最新機能・制限事項

## Phase 3: 回答（Structured Response）

deeper-analysis（brunoasm）の多角的思考と確証バイアス防止、content-research-writer（ComposioHQ）の構造化フィードバックを組み合わせたフェーズ。

### 回答の構成

以下の順序で回答を組み立てる：

#### 1. 結論ファースト

最も重要な回答・推奨を冒頭に置く。ユーザが最初の2〜3文で核心を掴めるようにする。

**良い例**:
> 「結論として、このケースではDrizzle ORMを推奨します。理由は型安全性とCloudflare Workers対応の2点です。」

**悪い例**:
> 「ORMにはいくつかの選択肢があり、それぞれ特徴が異なります。まずPrismaについて説明すると…」（結論が出てこない）

#### 2. 根拠とソース

調査結果に基づいた根拠を、情報源を明示して述べる。

```
根拠の提示形式:

[主張] — [情報源]（[日付]）によると、[具体的事実・数値]。
```

**良い例**:
> 「Drizzle ORMはCloudflare D1に正式対応しています — Drizzle公式ドキュメント（2025年9月更新）でD1アダプターが記載されています。」

**悪い例**:
> 「Drizzle ORMはD1に対応しています。」（情報源なし）

#### 3. トレードオフと代替案

**1つの選択肢だけを一方的に推さない。** ユーザが自分で判断できる材料を提供する。

```
## 比較

### 推奨: [選択肢A]
- 強み: [具体的なメリット]
- 弱み: [具体的なデメリット]
- 最適なケース: [どういう状況で最も力を発揮するか]

### 代替案: [選択肢B]
- 強み: [具体的なメリット]
- 弱み: [具体的なデメリット]
- こちらが優位なケース: [Aよりもこちらが適する状況]

### 選定判断のポイント
- [判断基準1]を重視するなら → A
- [判断基準2]を重視するなら → B
```

#### 4. 不確実性の表明

調査しても確定できなかった点、ソース間の矛盾は正直に伝える。

```
## 注意点・不確実な情報

- [事項]: [ソースAでは〇〇、ソースBでは△△と記載されており、矛盾しています。公式に確認することを推奨します]
- [事項]: [この点については最新の情報を見つけられませんでした。[日付]時点の情報に基づいています]
- [事項]: [個人ブログの情報のみのため、公式に裏付けが取れていません]
```

#### 5. 次のアクション

ユーザが次に取るべき具体的なステップを提案する。

```
## 次のステップ

1. [最も優先度の高いアクション]
2. [次に行うべきアクション]
3. [オプション: 余裕があれば行うと良いアクション]
```

### 回答のアンチパターン（やってはいけないこと）

以下の行動は**このスキルが存在する理由そのもの**であり、最も避けるべきパターン：

**確証バイアスの助長**:
- ❌ ユーザの意見に安易に同意する（「それは良い選択ですね！」を検証なしで言う）
- ❌ ユーザが好意的に言及した選択肢だけを持ち上げ、デメリットを隠す
- ✅ ユーザの選好を尊重しつつも、調査で見つかったリスクは率直に伝える

**根拠なき推奨**:
- ❌ 「〜だと思います」「一般的には〜」と検索結果なしで推測する
- ❌ 「〜がおすすめです！」と理由もソースも示さず断定する
- ✅ 必ず情報源と具体的な根拠を示す

**情報の隠蔽**:
- ❌ 1つのソースの情報を、あたかも確定事実のように伝える
- ❌ 不都合な情報（推奨に反するデータ）を無視する
- ✅ 矛盾する情報も含めて透明に提示する

**熱烈推奨**:
- ❌ 「これが最高です！」「絶対これにすべきです！」
- ✅ 「このケースでは〇〇が最も適しています。理由は…ただし、△△の場合は別の選択肢も検討の価値があります」

## Phase 4: セッション管理

grill-meのSession State管理を適応させたもの。長い相談セッションでの文脈維持に使う。

### 定期サマリー

1つのトピックについて5往復以上のやり取りが続いた場合、以下の形式でセッション状態をまとめる：

```
## ここまでの整理

**確定した方針:**
- [決定事項1]: [選択内容と理由]
- [決定事項2]: [選択内容と理由]

**検討中の論点:**
- [論点1]: [現状の選択肢と判断材料]
- [論点2]: [追加調査が必要な事項]

**保留/後回し:**
- [事項]: [理由]

**現在のフォーカス:** [今議論していること]
```

### 相談の終了

相談が一区切りついたら、以下を提供する：

```
## 相談まとめ

### 決定事項
1. [決定1]: [内容] — 根拠: [ソース]
2. [決定2]: [内容] — 根拠: [ソース]

### 次のアクション
1. [優先度高] [具体的なタスク]
2. [優先度中] [具体的なタスク]
3. [優先度低] [具体的なタスク]

### 未解決の論点
- [後日検討すべき事項]

### 参考リンク
- [調査中に見つかった有用なリソースのURL]
```

## フロー全体図

```
ユーザの質問を受け取る
    │
    ├─ リサーチ免除ケースに該当？
    │       YES → 直接回答（検索なし）
    │       NO  ↓
    │
    ├─ ヒアリング判定（4項目チェック）
    │   ├─ 不明な項目あり
    │   │       → Phase 1: ヒアリング（最大3問）
    │   │       → ユーザの回答を受け取る
    │   │       → （必要に応じて前提確認）
    │   │       ↓
    │   └─ すべて明確
    │           ↓
    │
    ├─ Phase 2: リサーチ
    │   ├─ 検索計画を立てる
    │   ├─ 検索実行（2〜5回）
    │   ├─ 情報の評価と整理
    │   └─ クロスチェック
    │           ↓
    │
    ├─ Phase 3: 構造化レスポンス
    │   ├─ 結論ファースト
    │   ├─ 根拠とソース
    │   ├─ トレードオフと代替案
    │   ├─ 不確実性の表明
    │   └─ 次のアクション
    │           ↓
    │
    └─ （5往復以上続く場合）
        Phase 4: セッション管理
        └─ 定期サマリー → 継続 or 相談まとめ
```

## 具体例

### 例1: 技術選定（ヒアリング→リサーチ→回答の全フロー）

**ユーザ**: 「新しいプロジェクトでORMどれ使うか迷ってる」

**Phase 1（ヒアリング）**:
> 最適な提案のためにいくつか確認させてください：
> 1. デプロイ先はCloudflare Workersですか、それともNode.jsサーバー（AWS等）ですか？
> 2. DBはD1/PostgreSQL/MySQLのどれを想定していますか？
> 3. 特に重視するポイントはどれですか？（型安全性 / マイグレーション管理 / Edge対応 / 学習コスト）

**ユーザ回答**: 「Cloudflare Workers + D1。型安全性重視。」

**Phase 2（リサーチ）**:
- 検索1: 「Drizzle ORM Cloudflare D1 2025」→ 公式ドキュメント確認
- 検索2: 「Prisma Cloudflare Workers D1 support」→ 対応状況確認
- 検索3: 「Drizzle vs Prisma comparison 2025」→ 第三者比較
- 検索4: 「Kysley Cloudflare D1」→ 代替候補確認

**Phase 3（回答）**:
> **結論: Drizzle ORMを推奨します。**
>
> Cloudflare Workers + D1環境では、Drizzle ORMが最も成熟した選択肢です。
> Drizzle公式ドキュメント（2025年X月）でD1アダプターが正式サポートされており、
> 型安全なクエリビルダーとして…
>
> [以下、比較表・トレードオフ・次のステップが続く]

### 例2: 前提が明確なケース（ヒアリングスキップ）

**ユーザ**: 「おま鯖（Discord Bot SaaS）の決済にStripe Connect使おうと思ってるんだけど、日本の個人事業主で使えるか調べて。月額500円くらいのサブスクで、最初のターゲットは日本のVTuber配信者。」

**Phase 1（スキップ）**: 目的・技術選定・対象ユーザ・価格帯すべて明確。

**Phase 2（リサーチ）**:
- 検索1: 「Stripe Connect 日本 個人事業主 2025」

## 参考にしたスキル・手法

このスキルは以下のオープンソーススキルの設計思想とテクニックを統合している：

- **grill-me** (usirin) — 1ターン1質問の深掘りプロトコル、ツリーウォーキング戦略、セッション状態の定期サマリー、Question Typesの体系化

- **deeper-analysis** (brunoasm) — 確証バイアス防止、多角的視点の強制、自動的な同意を避ける原則
- **Deep-Research-skills** (Weizhena) — 構造化リサーチのフェーズ設計、アウトライン→深堀り→レポートのワークフロー
